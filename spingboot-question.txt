6. What is Auto configuration in spring boot ?
Spring Boot auto-configuration is a powerful mechanism that automatically configures a Spring application based on the dependencies present in the project's classpath.
Classpath Scanning:
                    When your application starts, Spring Boot scans the classpath to detect specific classes and JAR dependencies (
                    e.g., HSQLDB, Spring MVC, JPA libraries).
Loading Auto-Configuration Classes:
                                    It finds potential auto-configuration classes listed in a special metadata file
                                    (in Spring Boot 2.7+ it's META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.
                                    imports, in older versions it was META-INF/spring.factories) within the dependency JARs.
Conditional Logic:
                    Each potential auto-configuration class uses conditional annotations to determine if it should be applied.
                    These conditions check:Presence or absence of specific classes on the classpath (@ConditionalOnClass or
                    @ConditionalOnMissingClass).Presence or absence of specific beans in the application context (@ConditionalOnBean
                    or @ConditionalOnMissingBean). This allows user-defined beans to always take precedence over auto-configuration defaults.
                    Specific property settings in application.properties or application.yml (@ConditionalOnProperty).
Bean Registration:
                If all conditions for an auto-configuration class are met,the beans defined within that class are
                registered in the application context, effectively configuring the feature with smart defaults.

9. How Spring boot run() method works internally ?
The run() method in Spring Boot is the entry point for launching a Spring application. It performs several key steps to initialize and start the application:
    1. Create an ApplicationContext: The run() method creates an instance of the appropriate ApplicationContext (e.g., AnnotationConfigApplicationContext for a standard Spring application or SpringApplicationContext for a Spring Boot application).
    2. Register Shutdown Hook: It registers a shutdown hook to ensure that the application context is properly closed when the JVM shuts down.
    3. Refresh the ApplicationContext: The run() method refreshes the application context, which involves loading all bean definitions, creating and initializing beans, and performing dependency injection.
    4. Run CommandLineRunners and ApplicationRunners: If there are any beans that implement CommandLineRunner or ApplicationRunner, their run() methods are executed after the application context is fully initialized. This allows you to perform custom logic or initialization tasks at startup.
    5. Return the ApplicationContext: Finally, the run() method returns the fully initialized ApplicationContext, which can be used to interact with the application and access beans.

14. How many ways we can perform dependency injection in spring or spring boot ?
There are three main ways to perform dependency injection in Spring or Spring Boot:
    Constructor Injection: Dependencies are provided through the constructor of a class. This is the most recommended approach as it allows for immutable dependencies and makes it easier to write unit tests.
    Setter Injection: Dependencies are provided through setter methods after the object is constructed. This approach allows for optional dependencies but can lead to mutable state if not used carefully.
    Field Injection: Dependencies are injected directly into the fields of a class using annotations like @Autowired. While this approach is concise, it is generally discouraged as it can make testing more difficult and can lead to issues with immutability and encapsulation.

15. where you would choose to use setter injection over constructor injection, and vice versa ?
Constructor Injection is generally preferred when:
    Dependencies are required and should not be null.
    You want to create immutable objects.
    You want to ensure that all dependencies are provided at the time of object creation, making it easier to write unit tests.
Setter Injection is generally preferred when:
    Dependencies are optional and can be set after object creation.
    You want to allow for mutable state in the object.
    You want to provide a default constructor for frameworks that require it (e.g., for serialization or proxying).

23. How will you resolve bean dependency ambiguity ?

To resolve this issue, you can use the @Qualifier annotation to specify which bean should be injected. For example:
    @Autowired
    @Qualifier("specificBeanName")
    private MyService myService;
Alternatively, you can also use the @Primary annotation on one of the beans to indicate that it should be the default choice when multiple beans of the same type are present. For example:
    @Bean
    @Primary
    public MyService primaryMyService() {
        return new MyServiceImpl1();
    }
    @Bean
    public MyService secondaryMyService() {
        return new MyServiceImpl2();
    }
In this case, if you autowire MyService without using @Qualifier, the primaryMyService bean will be injected by default, resolving the ambiguity.

25. What is bean scope & Can you explain different type of bean scope ?
Bean scope in Spring defines the lifecycle and visibility of a bean within the application context. It determines how many instances of a bean are created and how they are shared across the application. The different types of bean scopes in Spring are:
    Singleton: This is the default scope. Only one instance of the bean is created for the entire application context, and it is shared across all components that require it.
    Prototype: A new instance of the bean is created every time it is requested from the application context. This means that each component that requires the bean will get a new instance.
    Request: A new instance of the bean is created for each HTTP request. This scope is typically used in web applications to ensure that each request has its own instance of a bean.
    Session: A new instance of the bean is created for each HTTP session. This scope is also used in web applications to maintain state across multiple requests within the same session.
    Application: A single instance of the bean is created for the entire application, and it is shared across all sessions and requests. This scope is typically used for beans that need to be shared across the entire application, such as configuration beans or services that manage global state.
    Websocket: A new instance of the bean is created for each WebSocket connection. This scope is used in applications that use WebSockets to maintain state for each connection.

29. What is the difference between spring singleton and plain singleton ?
A plain singleton is a design pattern where a class is designed to have only one instance throughout the application.
  This is typically achieved by making the constructor private and providing a static method to access the single instance.
  However, this approach does not provide any built-in support for dependency injection, lifecycle management, or other features that are
  commonly needed in modern applications.
On the other hand, a Spring singleton is a bean scope in the Spring Framework where only one instance of a bean is created and shared
    across the entire application context. Spring manages the lifecycle of the singleton bean, including its creation, initialization,
    and destruction. Additionally, Spring provides support for dependency injection, allowing you to easily manage dependencies between beans.
    The Spring singleton scope also allows for more flexibility and configurability compared to a plain singleton, as you can define the
    behavior of the singleton bean using annotations or XML configuration.

36. Why did you use @RestController why not @Controller ?
@RestController is a specialized version of the @Controller annotation in Spring. It is used to create RESTful web services and is a combination of @Controller and @ResponseBody annotations. When you use @RestController, it automatically converts the return value of the methods into JSON or XML format (depending on the client's request) and sends it as the response body. This eliminates the need to annotate each method with @ResponseBody, making it more convenient for building RESTful APIs.
On the other hand, @Controller is a more general annotation used for traditional MVC controllers that return views (e.g., JSP, Thymeleaf) rather than data. If you use @Controller, you would need to annotate each method with @ResponseBody to indicate that the return value should be serialized and sent as the response body, which can be more verbose when building RESTful APIs. Therefore, using @RestController is more appropriate when you are building RESTful web services that primarily return data rather than views.

40. How can we perform content negotiation (XML/JSON) in Rest endpoint ?
In Spring Boot, you can perform content negotiation in a REST endpoint by using the @RequestMapping annotation along with the produces attribute to specify the supported media types (e.g., application/json, application/xml). Spring will automatically handle the content negotiation based on the client's request headers (Accept header) and return the response in the appropriate format. Here's an example of how to implement content negotiation:
    @RestController
    @RequestMapping("/api/products")
    public class ProductController {
        @GetMapping(produces = { MediaType.APPLICATION_JSON_VALUE, MediaType.APPLICATION_XML_VALUE })
        public List<Product> getAllProducts() {
            // Logic to retrieve and return all products
            return productService.getAllProducts();
        }
    }
In this example, the getAllProducts method is annotated with @GetMapping and specifies that it can produce both JSON and XML responses. When a client makes a request to this endpoint, Spring will check the Accept header in the request to determine which format the client prefers. If the client requests application/json, Spring will return the response in JSON format. If the client requests application/xml, Spring will return the response in XML format. If the client does not specify an Accept header, Spring will use a default media type (usually JSON) to return the response.     Content Negotiation Versioning: In this approach, the version number is included in the Accept header of the request. For example, clients can specify Accept: application/vnd.example.v1+json or Accept: application/vnd.example.v2+json to indicate which version of the API they want to use.
The choice of versioning strategy depends on your specific use case and preferences. URI versioning is
often considered the most straightforward and easy to understand, while header versioning and content negotiation can provide more flexibility without cluttering the URI. It's important to consistently apply the chosen versioning strategy across your API and communicate the versioning approach clearly to your clients. Additionally, you should consider deprecating older versions of the API gracefully and providing clear documentation on how clients can migrate to newer versions when necessary.

57. What is AOP ?
AOP (Aspect-Oriented Programming) is a programming paradigm that allows you to separate cross-cutting concerns from the main business logic
 of your application. It provides a way to modularize aspects of your application that cut across multiple components, such as
 logging, security, transaction management, and performance monitoring. AOP enables you to define reusable pieces of code
 (called "aspects") that can be applied to various parts of your application without modifying the core business logic.
In AOP, you can define "advice" (the code to be executed) and "pointcuts" (the points in the application where the advice should be applied). This allows you to apply the same behavior across multiple methods or classes without duplicating code, making your application more modular and easier to maintain. AOP is commonly used in Spring Framework to implement cross-cutting concerns in a clean and efficient way, allowing developers to focus on the core business logic while still addressing important concerns in a consistent manner across the application.

58. What is pointcut & join Points in AOP ?
In AOP (Aspect-Oriented Programming), a "pointcut" is a predicate that matches join points. It defines where the advice should be applied in the application. Pointcuts are used to specify the conditions under which advice should be executed, such as matching method executions, field access, or constructor calls. For example,
    you can define a pointcut that matches all methods in a specific package or all methods annotated with a certain annotation.
A "join point" is a specific point in the execution of the program where an aspect can be applied. Join points can be method executions, field access, constructor calls, or even exception handling. When a join point is reached during the execution of the program, the corresponding advice defined in the aspect will be executed if the join point matches the conditions specified in the pointcut. In summary, pointcuts define where advice should be applied, while join points are the actual points in the program's execution where the advice can be executed based on the defined pointcuts.

59. What are different type of advice ?
In AOP (Aspect-Oriented Programming), there are several types of advice that can be applied to join points. The main types of advice include:
    1. Before Advice: This type of advice is executed before the join point is reached. It allows you to perform actions or checks before the actual method execution takes place.
    2. After Advice: This advice is executed after the join point has completed, regardless of whether it completed successfully or threw an exception. It can be used for cleanup activities or logging.
    3. After Returning Advice: This advice is executed only if the join point completes successfully without throwing an exception. It allows you to access the return value of the method and perform actions based on it.
    4. After Throwing Advice: This advice is executed only if the join point throws an exception. It allows you to handle exceptions and perform error logging or recovery actions.
    5. Around Advice: This is the most powerful type of advice, as it allows you to control when and if the join point is executed. You can perform actions before and after the method execution, and even choose not to execute the method at all based on certain conditions.
Each type of advice serves a specific purpose and can be used to address different cross-cutting concerns in your application, such as logging, security, transaction management, or performance monitoring. By using these different types of advice, you can modularize your code and keep the core business logic separate from the cross-cutting concerns, making your application more maintainable and easier to understand.

76. What is transaction management and how it works ?
Transaction management is a critical aspect of software development that ensures the integrity and consistency of data when performing multiple operations that need to be treated as a single unit of work. A transaction is a sequence of operations that are executed as a single logical unit, and it must either be fully completed (committed) or fully rolled back in case of an error or failure. This ensures that the system remains in a consistent state even in the presence of errors or concurrent access.
In Spring Boot, transaction management is typically handled using the @Transactional annotation, which can be applied to methods or classes to indicate that the operations within should be executed within a transaction. When a method annotated with @Transactional is called, Spring will start a new transaction if one does not already exist. If an exception occurs during the execution of the method, Spring will automatically roll back the transaction to ensure that no partial changes are persisted to the database. If the method completes successfully, Spring will commit the transaction, making all changes permanent.
Spring's transaction management can be configured to work with various transaction managers, such as DataSourceTransactionManager for JDBC, JpaTransactionManager for JPA, and others. This allows you to manage transactions across different types of data sources and persistence technologies. Additionally, Spring provides support for declarative transaction management, which allows you to define transaction boundaries and behavior using annotations or XML
configuration, making it easier to manage transactions without having to write explicit transaction management code. Overall, transaction management is essential for ensuring data integrity and consistency in applications that perform multiple related operations, and Spring Boot provides robust support for managing transactions effectively.

78. What are different type of Isolation and Propagation ?
In Spring Framework, transaction isolation and propagation are important concepts that define how transactions interact with each other and how they manage concurrent access to data. Here are the different types of isolation and propagation:
1. Isolation Levels:
    - READ_UNCOMMITTED: This is the lowest isolation level, where transactions can read uncommitted changes made by other transactions. This can lead to issues like dirty reads, non-repeatable reads, and phantom reads.
    - READ_COMMITTED: In this isolation level, transactions can only read committed changes made by other transactions. This prevents dirty reads but can still allow non-repeatable reads and phantom reads.
    - REPEATABLE_READ: This isolation level ensures that if a transaction reads a row, it will see the same data for that row throughout the transaction, even if other transactions modify it. This prevents dirty reads and non-repeatable reads but can still allow phantom reads.
    - SERIALIZABLE: This is the highest isolation level, where transactions are completely isolated from each other. It prevents dirty reads, non-repeatable reads, and phantom reads by ensuring that transactions are executed in a serial order. However, it can lead to reduced concurrency and performance issues.
2. Propagation Levels:
    - REQUIRED: This is the default propagation level, where the method will join an existing transaction if one exists, or create a new transaction if none exists.
    - REQUIRES_NEW: This propagation level creates a new transaction, suspending any existing transaction. This is useful when you want to execute a block of code in a separate transaction, independent of the current transaction.
    - SUPPORTS: This propagation level allows the method to execute within a transaction if one exists, but it will execute non-transactionally if no transaction exists.
    - NOT_SUPPORTED: This propagation level suspends any existing transaction and executes the method non-transactionally.
    - MANDATORY: This propagation level requires that a transaction already exists. If no transaction exists, an exception will be thrown.
    - NEVER: This propagation level ensures that the method is executed non-transactionally. If a transaction exists, an exception will be thrown.
    - NESTED: This propagation level allows the method to execute within a nested transaction if an existing transaction exists. If no transaction exists, it behaves like REQUIRED and creates a new transaction. Nested transactions can be rolled back independently of the outer transaction, which can be useful for certain use cases.
By understanding and using the appropriate isolation and propagation levels, you can effectively manage transactions in your Spring Boot application, ensuring data integrity and consistency while optimizing performance based on the specific requirements of your application.

Handling transactions in a distributed microservices architecture can be complex due to the need to maintain data consistency across multiple services. Here are some approaches to manage transactions in such an environment:
1. Two-Phase Commit (2PC): This is a traditional approach where a coordinator manages the transaction across multiple services. The coordinator first asks all participating services to prepare for the transaction (phase one), and if all services respond positively, it then commits the transaction (phase two). However, this approach can be slow and may lead to performance issues due to the need for coordination and potential for blocking.
2. Sagas: A more modern approach to handling transactions in microservices is the Saga pattern. In this pattern, a long-running transaction is broken down into a series of smaller, independent transactions that are executed sequentially. Each transaction updates the state of the system and publishes an event to trigger the next transaction. If any transaction fails, compensating transactions are executed to undo the changes made by the previous transactions. This approach allows for better performance and scalability while still maintaining data consistency.
3. Eventual Consistency: In some cases, it may be acceptable to have eventual consistency rather than strong consistency. This means that changes made in one service may not be immediately reflected in other services, but they will eventually become consistent. This approach can be simpler to implement and can provide better performance, but it may not be suitable for all use cases, especially those that require immediate consistency.
4. Distributed Transactions with Messaging: Another approach is to use messaging systems (e.g., Kafka, RabbitMQ) to manage distributed transactions. Services can publish events to a message broker, and other services can subscribe to those events to perform their part of the transaction. This allows for loose coupling between services and can help manage transactions across multiple services without the need for a central coordinator.
5. Use of Distributed Transaction Managers: Some frameworks and tools provide support for distributed transactions, such as Atomikos or Narayana. These tools can help manage transactions across multiple services and data sources, but they may add complexity to the system and may not be suitable for all use cases.
Overall, the choice of transaction management strategy in a distributed microservices architecture depends on the specific requirements of your application, including the need for consistency, performance, and scalability. It is important to carefully evaluate the trade-offs of each approach and choose the one that best fits your use case while ensuring that data integrity and consistency are maintained across your microservices.

81. Can we use transaction in multiple microservices why or why not ?
In a distributed microservices architecture, using transactions across multiple microservices can be challenging due to the need to maintain data consistency and integrity across different services. While it is technically possible to use transactions in multiple microservices, it is generally not recommended due to the complexity and potential performance issues that can arise. Here are some reasons why:
1. Distributed Transactions Complexity: Managing transactions across multiple microservices requires a distributed transaction coordinator, which
can add significant complexity to the system. Coordinating transactions across services can lead to issues such as increased latency, potential for deadlocks, and difficulties in handling failures.
2. Performance Issues: Distributed transactions can significantly impact the performance of the system, as they require
synchronization between services and can lead to blocking operations. This can result in slower response times and reduced throughput, especially in high-traffic applications.
3. Scalability Challenges: Using transactions across multiple microservices can limit the scalability of the system
because it requires coordination between services, which can become a bottleneck as the number of services and transactions increases.
4. Eventual Consistency: In a microservices architecture, it is often more practical to embrace eventual consistency rather than trying to maintain strong consistency across services. This allows for better performance and scalability while still ensuring that data will eventually become consistent across services. Using transactions across multiple microservices can make it difficult to achieve eventual consistency and can lead to issues with data integrity if not managed carefully.
5. Alternative Approaches: Instead of using transactions across multiple microservices, it is often better to use patterns such as Sagas or event-driven architectures to manage data consistency across services. These approaches allow for better performance and scalability while still maintaining data integrity without the need for distributed transactions.
In summary, while it is possible to use transactions across multiple microservices, it is generally not recommended due to the complexity, performance issues, and scalability challenges that can arise. Instead, it is often better to use alternative approaches that are more suitable for a distributed microservices architecture, such as Sagas or event-driven architectures, to manage data consistency across services while maintaining performance and scalability.
